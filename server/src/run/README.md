# Run coordinator

## Overview

The run module contains the application services for durable Droid runs. [`coordinator`](coordinator.rs) creates idempotent run records, validates state transitions, replays event pages, and applies recovery decisions from persisted app-server evidence. [`policy`](policy.rs) resolves the effective Droid permissions as a subset of the project ceiling and builds a named, default-deny Codex profile for an isolated app-server process. The profile maps canonical project/reference roots, restricted write roots, web search, and shell network separately; Windows prefers MXC and fails closed if the profile cannot be enforced. [`codex_app_server`](codex_app_server.rs) starts the local Codex app-server over stdio with that profile and exposes thread/turn and server-owned command methods. [`worker`](worker.rs) handles one Droid turn followed by a server-owned verification preset. Run submission is authenticated and the worker is disabled unless `GRID_METROPOLIS_RUNS_ENABLED=true`. Known command/file-change approvals are persisted and pause the worker until an authenticated decision is acknowledged; unknown app-server request methods are declined. On restart, an unsent approval can resume only when the saved item exists in an incomplete turn with no completed mutation. The worker then reissues the original turn and compares the canonical action fingerprint before reusing the approval. [`dispatcher`](dispatcher.rs) routes decisions only to the matching run/request session. [`recovery`](recovery.rs) reconciles nonterminal runs before the HTTP server starts. The SQLite repository commits each state change with its event. [`budget`](budget.rs) evaluates hard turn/time ceilings and the approved best-effort token ceiling.

## Invariants

- Only the defined sequential state transitions are accepted; terminal states cannot transition again (`domain/run.rs::RunStatus::can_transition_to`).
- Run creation freezes the configured project budget and requires assigned droids and a project verification preset; `(projectId, idempotencyKey)` identifies an identical retry.
- State changes and lifecycle events commit in one SQLite transaction; event sequences are increasing per run.
- The app-server thread ID is write-once for a run; repeating the same ID is idempotent, while changing it conflicts. Attachment and its audit event are atomic.
- Startup recovery keeps queued runs that have no thread or step and retains a persisted, unsent permission request. In-flight model steps persist their app-server turn ID and planned next state before completion. Recovery advances only when the same thread contains that completed turn, a timestamped final-answer item, and completed history entries for every permission operation whose grant was sent; the step result and next-state transition are then recorded in SQLite. Missing or mismatched evidence blocks the run.
- A later turn may reissue a pending operation only after comparing its canonical fingerprint with the persisted request (`domain/run.rs::evaluate_recovery`). Persisted completion advances only from a successful step record.
- Recovery only advances from a completed step record persisted as `SUCCEEDED`; pending approvals are checked against the stored request ID/fingerprint and decision/response state.
- Permission decisions are immutable and idempotent only when the same decision and `Idempotency-Key` are repeated. Recording a grant or denial leaves the run waiting until app-server confirms delivery; the acknowledgement then resumes the saved stage. Denying the fourth specific permission request blocks the run.
- Project budgets are required; a droid or run override may only lower the project values.
- Model-turn and elapsed-time limits are checked before each new turn.
- Token usage is best-effort: when provider telemetry reaches the configured value, the active turn is interrupted when possible and no later turn may start. A turn can overshoot before the telemetry arrives.
- Startup recovery runs before API routes accept requests. It never dispatches a model turn or executes a command. The worker requeues untouched `QUEUED` runs only when explicitly enabled; uncertain in-flight runs remain blocked for reconciliation.
- The profile builder has a live Windows Codex CLI probe proving project/read-reference access, configured write-root access, and denial outside those roots. The worker submits one Droid turn, persists known permission requests, waits for an authenticated grant/deny, and has a conservative restart path that blocks if the saved request item is absent, its turn is complete, any mutation in that turn already completed, or the reissued action fingerprint differs. After verification fails, it permits one focused repair turn and one rerun of the same preset if the run budgets still allow them. Independent Droid review and the UI flow remain before live runs can be enabled.
- Run submission accepts only the `cargo-test` and `npm-check` server-owned argv presets. A completed final-answer item and successful verification exit code are required before review; a failing first verification gets at most one repair and one verification rerun. Repair and the independent Reviewer consume the same model-turn, elapsed-time, and best-effort token ceilings. The Reviewer runs in a separate read-only app-server session and must return an explicit `APPROVE`; malformed or negative verdicts fail the run. Unknown approval methods are denied. UI and complete E2E validation remain outstanding. If the process restarts while review is unresolved, recovery blocks conservatively instead of rerunning the review.
